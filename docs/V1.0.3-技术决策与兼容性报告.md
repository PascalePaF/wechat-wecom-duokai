# V1.0.3 技术决策、兼容性与代码签名报告

文档编号：`WD-ADR-2026-09-13-V103`  
评估日期：2026-09-13（Asia/Tokyo）  
对象：`PascalePaF/wechat-wecom-duokai` V1.0.3

## 1. 结论先行

V1.0.3 继续使用 C#、WPF 与 .NET Framework 4.8，不迁移到 WinUI 3、Tauri 或 Python，也不在本版
切换到 WiX/MSI。这不是“维持不动”：本版已把最影响体验和安全的结构问题补齐，包括进程环境抽象、
签名校验式客户端选择、响应式窗口、Per-Monitor V2 DPI、运行中覆盖安装、独立清理器、本地诊断和
受限的 GitHub Release 检查。

代码签名方面，面向公众分发且希望 Windows 显示可信发布者时，通常需要付费或申请合资格的开源
签名服务。自签名证书免费，但普通用户的 Windows 不信任它，对公开发布几乎不能解决未知发布者和
SmartScreen 问题。对本项目最现实的顺序是：先申请 SignPath Foundation 的免费开源签名；不符合
条件时，再根据发布主体所在地区选择 Microsoft Artifact Signing 或传统 OV 证书。

## 2. 客户端兼容性策略

### 2.1 本版实际覆盖的客户端身份

| 客户端分支 | 主程序名 | 定位方式 | 单实例兼容路径 |
| --- | --- | --- | --- |
| 微信 3.x / 旧 Windows 分支 | `WeChat.exe` | 注册表、App Paths、运行进程、常见目录、手动选择 | 已知 WeChat 互斥锁 |
| 微信 4.x / 统一 Windows 分支 | `Weixin.exe` | 同上 | `xwechat\lock\lock.ini` 精确文件锁 + 已知 Weixin 互斥锁 |
| 企业微信现行 Windows 分支 | `WXWork.exe` | 注册表精确 Executable、App Paths、运行进程、常见目录、手动选择 | `multi_instances` 提示 + 已知独占互斥锁 |
| 企业微信兼容命名 | `WeCom.exe` / `企业微信.exe` | 仅在身份与签名共同通过时接受 | 与企业微信相同 |

本版不写“只支持 4.1.15.6”这样的版本白名单。维护版只要仍使用受支持的主程序身份、腾讯产品信息
和有效腾讯签名，就能被定位；底层锁处理根据实际产品代际而不是补丁号工作。

### 2.2 真机验证基线

2026-09-13 在当前机器核验：

| 客户端 | 文件 | 版本 | Authenticode |
| --- | --- | --- | --- |
| 微信 | `Weixin.exe` | `4.1.15.6` | Valid；Tencent Technology (Shenzhen) Company Limited |
| 企业微信 | `WXWork.exe` | `5.0.11.6018` | Valid；Tencent Technology (Shenzhen) Company Limited |

两者均被 V1.0.3 的运行时验证器接受。当前微信的三个界面实例会产生多组同名子进程；新的进程环境
依然按父子关系归并根进程，没有把十五个同名进程误算成十五个窗口。

### 2.3 “兼容所有官方可下载版本”的准确边界

本版以微信 Windows 的两代官方入口名和企业微信现行入口名为覆盖目标，并避免把补丁号写死。这能
覆盖当前正常安装的官方 Windows 客户端以及仍使用这些身份的维护版，但不能对腾讯未来尚未发布的
进程名、锁机制或商店沙箱变化作保证。若未来客户端改变单实例实现，本工具的原则是失败关闭并提示，
不会自动扩大到注入、远程线程、内存补丁或修改客户端文件。

微信官方下载入口：<https://weixin.qq.com/cgi-bin/readtemplate?t=weixin_pc_download-zh_CN>  
企业微信官方下载入口：<https://work.weixin.qq.com/#indexDownload>

## 3. 自定义微信路径为什么要三重验证

只检查 `Weixin.exe` 这个文件名不够安全，任何程序都可以被重命名。本版依次要求：

1. 文件名属于所选客户端的明确集合；
2. PE 版本资源里的公司、产品、描述或原始文件名同时指向 Tencent 和对应产品；
3. Windows `WinVerifyTrust` 对文件 Authenticode 返回有效，并且签名证书主体属于 Tencent。

验证使用缓存证书链且不为此主动联网。未签名、自签名、签名损坏、腾讯签名但产品类型不一致的文件
都会被拒绝。用户选择成功后保存完整路径；每次启动仍重新验证，不能靠一次通过永久绕过。

## 4. 代码签名是否需要花钱

### 4.1 代码签名解决什么

Authenticode 能证明“这个二进制由哪个已验证主体签发”以及“签名后内容是否被修改”。它不能证明
程序永远无漏洞，也不能替代源码审计和杀毒扫描。Microsoft 说明，相同受信任签名身份可以跨版本积累
发布者信誉；未签名软件每个新哈希都要从零建立信誉。即便使用 OV/EV 证书，新文件也仍可能在早期
出现 SmartScreen 信誉提示；自 2024 年起，EV 不再自动跳过这一过程。

Microsoft 官方说明：

- [Windows 应用代码签名选项](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)
- [SmartScreen 发布者与文件信誉](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- [SignTool 与 Smart App Control](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/code-signing-for-smart-app-control)

### 4.2 可选方案与成本

| 方案 | 直接费用 | 普通用户是否默认信任 | 适合本项目吗 |
| --- | ---: | --- | --- |
| 自签名证书 | 0 | 否；除非用户/企业预先安装根证书 | 仅开发测试，不作为公开 Release 方案 |
| Microsoft Store 的 MSIX | 商店对 MSIX 重新签名；签名本身免费 | 是 | 需先解决商店分发和全信任桌面能力评估；不是本版路线 |
| Microsoft Artifact Signing Basic | 官方列价约 US$9.99/月、每月 5,000 次签名 | 是；信誉仍需积累 | 地区与主体资格满足时很合适 |
| 传统 OV 证书 | Microsoft 概览约 US$150–300/年，供应商报价会变化 | 是；信誉仍需积累 | 地区不支持 Artifact Signing 时的标准路线 |
| EV 证书 | Microsoft 概览约 US$400+/年 | 是，但不再即时绕过 SmartScreen | 仅为 SmartScreen 不值得额外溢价 |
| SignPath Foundation 开源签名 | 合资格项目免费 | 证书显示 SignPath Foundation | **优先申请**，但需要项目审查和受控 CI 构建 |

Artifact Signing 官方价格页显示 Basic 为 US$9.99/月、Premium 为 US$99.99/月：
[Microsoft Artifact Signing SKU](https://learn.microsoft.com/en-us/azure/artifact-signing/how-to-change-sku)。
个人与组织的地区资格会变化，申请前应重新检查官方页面；不能根据本机时区假定用户一定有资格。

SignPath Foundation 明确提供免费的开源代码签名，但要求 OSI 许可、活跃维护、已发布版本、无恶意/
潜在不受欢迎行为、公开代码签名政策、GitHub 受信构建、角色分离和每次签名批准等条件：

- [SignPath Foundation](https://signpath.org/)
- [开源项目申请条件](https://signpath.org/terms.html)

本项目已具备 Apache-2.0、公开仓库、可重复构建脚本、版本化 Release、哈希和安全报告等基础，但底层
句柄关闭能力可能需要在申请材料中充分解释，由 SignPath 独立判断是否接受。

### 4.3 推荐实施顺序

1. 增加 GitHub Actions 的干净 Windows 构建、测试和来源证明；
2. 建立 `SECURITY.md`、代码签名政策、提交者/审核者/批准者角色；
3. 申请 SignPath Foundation；
4. 若未获接受，再按法律主体和地区选择 Artifact Signing Basic 或 OV；
5. 签名顺序必须是 Core DLL、主程序、独立清理器，最后签安装器；签后重新生成 SHA-256；
6. 使用 RFC 3161 时间戳，并在发布门禁中用 `Get-AuthenticodeSignature`/SignTool 验证每个产物。

## 5. 为什么本版不迁移 WinUI 3、Tauri 或 Python

| 方案 | 界面能力 | 新运行时/体积 | 对底层多开兼容的帮助 | 当前结论 |
| --- | --- | --- | --- | --- |
| WPF + .NET Framework 4.8 | 成熟矢量、模板、DPI、原生 HWND | 当前机器普遍具备 | 可直接调用既有 Windows API | 保留并完善 |
| WinUI 3 | Windows 11 风格更原生 | Windows App SDK 部署复杂度上升 | 不改变锁机制 | 暂不迁移 |
| Tauri | Web UI 灵活 | WebView2 + Rust 工具链 | 不改变锁机制 | 对小型工具收益不足 |
| Python | 开发快 | 打包体积、启动、AV 信誉成本明显 | Windows 句柄仍需原生封装 | 不适合发行形态 |

V1.0.2 的锯齿根因已经通过 WPF 修复；V1.0.3 又将 `TextFormattingMode` 改为 `Ideal`、关闭对矢量容器
不必要的像素吸附，并加入 Per-Monitor V2。现阶段换框架会增加依赖和新哈希面，却不能减少最敏感的
Windows 句柄操作，所以收益不成立。

## 6. WiX/MSI 评估

### 6.1 MSI 的真实优势

- Windows Installer 的组件数据库、回滚、修复、升级代码和企业部署能力更标准；
- Restart Manager 可以识别占用待更新文件的应用，并在完整 UI 中显示 Files-in-Use 选择；
- 适合组策略、软件清单、标准静默参数和长期企业运维。

Microsoft 的 Restart Manager 文档说明，MSI 可提供 `MsiRMFilesInUse` 对话框，让用户选择关闭并重启
占用文件的应用：
[Using Windows Installer with Restart Manager](https://learn.microsoft.com/en-us/windows/win32/msi/using-windows-installer-with-restart-manager)。

### 6.2 当前不迁移的原因

- 本项目当前是无管理员权限的当前用户安装，只有 3 个运行文件和少量快捷方式/注册表；
- “完整清理发布包并可选删除源码”不是标准 MSI 产品卸载职责，仍需独立清理器；
- 本版已经按精确安装路径实现了用户确认关闭，比为一个小版本引入整套 MSI 更直接；
- 未完成代码签名和 Windows Sandbox/虚拟机升级矩阵前，换安装技术会同时改变太多变量；
- WiX 当前发布与维护条款需要发布时重新确认。官方文档说明 WiX 生成 MSI/EXE，并提示营收使用的
  Open Source Maintenance Fee；截至所查页面，年营收超过 US$10,000 的组织需参与维护费。

参考：

- [WiX Toolset 官方概览](https://docs.firegiant.com/wix/)
- [WiX Open Source Maintenance Fee](https://docs.firegiant.com/wix/osmf/)

### 6.3 决策

V1.0.3 保留自有 WPF 安装器；把 WiX/MSI 列为“企业分发触发项”，不是普通用户路线。满足以下任一
条件后再做 PoC：需要组策略批量部署、需要 MSI 自动修复/回滚、安装文件超过当前简单模型，或已有稳定
签名 CI。PoC 应保留当前便携 ZIP，并让 MSI 只卸载安装产品，不承担删除源码的职责。

## 7. 本地诊断设计

入口只占页脚一个“诊断”文本按钮。点击后才创建：

```text
<程序目录>\diagnostics\diagnostic-yyyyMMdd-HHmmss.txt
```

内容限于助手版本、Windows/.NET/位数、已选择客户端路径、产品版本、腾讯签名结果、检测实例数和
兼容策略说明。不会收集聊天、联系人、账号、进程命令行、环境变量或浏览器数据，不会上传。安装版
位于用户可写目录时可正常写入；若用户把绿色版放进无写权限目录，会明确提示失败而不改写别处。

## 8. 更新检查的网络边界

启动后最多发起一次 HTTPS GET：

```text
https://api.github.com/repos/PascalePaF/wechat-wecom-duokai/releases/latest
```

只解析 `tag_name`，超时为 8 秒；失败不弹窗、不影响多开。按钮永远只打开：
`https://github.com/PascalePaF/wechat-wecom-duokai/releases`。没有附件下载、后台替换、执行 Release 文件、
遥测或诊断上传。因此它是“自动检测 + 浏览器手动下载”，不是自动更新器。

## 10. 后续优先级

1. 申请 SignPath Foundation，并建立 GitHub Actions 干净构建与签名审批链；
2. 用 Windows Sandbox 验证全新安装、V1.0.2→V1.0.3 覆盖、取消关闭、正常关闭、强制关闭和卸载；
3. 收集不同官方微信 3.x/4.x 与企业微信维护版本的匿名“版本 + 成功/失败”兼容结果；
4. 给底层句柄策略增加显式“标准/兼容”模式，让企业用户可以禁用句柄关闭；
5. 只有企业 MSI 需求出现后，再建立 WiX PoC，避免当前发行链同时维护两套安装数据库。
