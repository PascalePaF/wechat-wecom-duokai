# V1.0.4 企业微信三开与界面缩放验证报告

文档编号：`WD-VAL-2026-09-14-V104`  
验证日期：2026-09-14（Asia/Tokyo）  
对象：`PascalePaF/wechat-wecom-duokai` V1.0.4

## 1. 结论

V1.0.4 已在当前电脑的官方企业微信 `WXWork.exe 5.0.11.6018` 上成功得到 3 个同时运行的根实例。
实验证明，单独把 `HKCU\SOFTWARE\Tencent\WXWork\multi_instances` 写成 `3` 并不能突破当前客户端的
双开上限；有效路径是：启动阶段临时不使用这条注册表提示，在每次补开前只关闭企业微信进程中名称
匹配 `Tencent.WeWork.ExclusiveObject*` 的独占互斥锁，短暂等待后再启动下一个官方程序实例。

这不是修改客户端、内存注入或通用“破解”。V1.0.4 没有修改 `WXWork.exe`，没有写企业微信进程内存，
没有结束现有企业微信进程，也没有提升权限。程序只对当前 Windows 会话、可执行路径精确等于已验证
官方客户端的进程执行白名单句柄操作。

界面方面，WPF 足以实现本次要求，无需迁移技术栈。主窗口以 `901×513` 为最小基准，删除外层滚动条；
窗口放大后使用统一缩放因子处理整棵视觉树，并把因屏幕长宽比产生的额外空间交给内部比例网格。因此
3440×1392 下控件约放大 2.71 倍，同时左右区域铺满可用宽度，不再只在屏幕顶部保留一排小控件。

## 3. A/B 真机试验

### 3.1 方案 A：沿用 V1.0.3 的任意数值写法

步骤：

1. 将目标数设为 3；
2. 写入 `multi_instances=3`；
3. 沿用精确进程路径、根实例统计和已知锁释放逻辑；
4. 请求启动三个实例。

结果：

| 指标 | 数值 |
| --- | ---: |
| 请求目标 | 3 |
| 发出的启动请求 | 3 |
| 已处理的匹配锁 | 2 |
| 最终根实例 | 2 |
| 是否达到目标 | 否 |

结论：当前企业微信把该注册表入口当作双开功能，而不是任意实例数量参数。写 `3` 仍被限制为两个；
“继续提高注册表数值”不是有效方案，也不应永久改变用户配置。

### 3.2 方案 B：无双开提示 + 精确互斥锁交接

步骤：

1. 保持 `multi_instances` 不存在；
2. 启动第一个官方 `WXWork.exe`；
3. 在同一路径、同一会话的企业微信进程中查找并释放已知独占互斥锁；
4. 等待 100ms 后启动下一个实例；检测到新根实例后等待 800ms，再进行下一轮；
5. 重复到目标 3。

结果：

| 轮次 | 启动前根实例 | 本轮释放锁 | 启动后根实例 |
| ---: | ---: | ---: | ---: |
| 1 | 0 | 0 | 1 |
| 2 | 1 | 2 | 2 |
| 3 | 2 | 2 | 3 |

最终同时检测到 3 个根 PID：`11148`、`54764`、`34660`。随后通过窗口正常关闭请求退出三个测试实例；
最后一个窗口在主界面就绪后完成正常退出，六秒复核时剩余 `WXWork` 进程为 0。

V1.0.4 Core 编译完成后又执行了一次集成复核，不再手工拼接步骤：`InstanceManager` 从 0 请求目标 3，
返回 `Success=True`、`Before=0`、`After=3`、`Started=3`、`ReleasedLocks=4`。本轮三个新进程也全部
通过正常窗口关闭退出，复核剩余新进程为 0；`multi_instances` 在调用前后均不存在。

## 4. V1.0.4 的正式实现

### 4.1 短期注册表会话

新增 `IWeComLaunchPolicy`，把企业微信准备行为与进程编排分开。生产实现的规则是：

| 目标数量 | 启动期间行为 | 启动结束 |
| ---: | --- | --- |
| 1 | 不改注册表 | 无需恢复 |
| 2 | 临时设为 DWORD `2`，使用官方双开提示 | 恢复原值、原类型；原本不存在则删除 |
| 3–10 | 临时删除 `multi_instances`，避免被官方双开路径封顶 | 恢复原值、原类型；原本不存在则保持不存在 |

策略使用当前会话命名信号量串行化同一用户下多个助手的短期注册表操作。等待在后台执行，不阻塞主
界面；信号量释放也不依赖异步续体是否回到原线程。所有启动代码位于 `using/finally`
作用域内，正常完成、启动异常和取消都会进入恢复逻辑。注册表本身不可访问时，程序不会崩溃，而是只
尝试精确锁路径；恢复也属于尽力而为，因此报告不能把 Windows 权限或第三方同时改写时的恢复描述为
数学上的绝对保证。

### 4.2 锁白名单

当前官方二进制可见的相关名称包括：

- `Tencent.WeWork.ExclusiveObject`
- `Tencent.WeWork.ExclusiveObjectInstance1`
- `Tencent.WeWork.ExclusiveObjectInstance2`
- `Tencent.WeWork.ExclusiveVidObject.`

V1.0.4 只接受包含 `Tencent.WeWork.ExclusiveObject` 的互斥锁名称，视频对象不在白名单内。句柄源进程
还必须同时满足：当前用户会话、已知企业微信进程名、可读取的完整路径与当前已验证 `WXWork.exe`
路径一致。无法读取路径时失败关闭，不会扩大到“所有同名进程”。

### 4.3 可测试边界

自动测试不依赖真实企业微信即可验证：

- 原值为字符串时，扩展启动期间临时删除，结束后按原字符串类型恢复；
- 原值不存在时，双开期间临时出现 DWORD 2，结束后不残留；
- 固定进程环境从 1 个根实例增量达到 3 个，而不是重复启动三个；
- 100ms 锁交接与 800ms 实例稳定等待都被调用；
- 注册表启动会话恰好进入一次并释放一次。

## 6. 界面比例缩放设计

### 6.1 为什么上一版最大化后会显得空

V1.0.3 只让网格容器变宽，字体、图标、按钮、圆角与固定卡片尺寸仍保持原始 DIP 大小。3440×1392
屏幕因此把控件压成顶部的一条细带，大量高度没有参与布局；这不是 WPF 的能力限制，而是布局策略错误。

### 6.2 新算法

设当前窗口外框宽高为 `W`、`H`，最低基准为 `901×513`：

```text
scale = max(1, min(W / 901, H / 513))
logicalWidth  = viewportWidth  / scale
logicalHeight = viewportHeight / scale
```

整个主视觉树使用相同的 `scale`，不会横向拉胖文字或纵向拉长图标。逻辑画布再使用逆向尺寸填满实际
视口，屏幕长宽比多出来的空间由应用卡片与数量卡片按 `2.4:1` 的星号列比例吸收。这样同时满足：

- 小于基准时不再缩小，Windows 直接执行最低尺寸约束；
- 901×513 保持用户参考图的视觉密度；
- 1920×1080 与 3440×1392 中所有控件共同放大；
- 超宽屏横向空间被卡片消化，而不是留成窗口外部空白；
- 不需要 `ScrollViewer`，计数卡片永远位于最右侧；
- `ScaleX == ScaleY`，不会产生非等比变形。

### 6.3 WPF 继续适用

WPF 的矢量边框、文字排版、动态资源和 Per-Monitor V2 DPI 足以完成本次需求。继续使用现有框架避免
引入 WebView2、Windows App SDK 或 Python 打包运行时，也避免扩大未签名程序的依赖和安全扫描面。
本次没有迁移 WinUI 3、Tauri 或 Python。

## 8. 适用边界与风险

1. 本次只真机验证 3 个企业微信根实例；界面最大值 10 不等于每个版本都保证十开。
2. 腾讯没有公开承诺第三方锁交接机制；未来版本可改变锁名、进程模型或风险控制。
3. 多开可能受企业组织策略、账号风控、设备管理或客户端许可约束；用户应先用测试账号验证并遵守规则。
4. `NtQuerySystemInformation`/`NtQueryObject` 属于底层 Windows 接口，系统更新可能改变可用性。
5. 安全软件可能把跨进程句柄枚举/关闭视为启发式风险；应核对源码、SHA-256 和扫描结果，不能要求用户
   关闭防护或直接忽略明确告警。
6. 失败时程序只报告未达到目标，不会扩大白名单、注入客户端、修改二进制或结束现有会话。
