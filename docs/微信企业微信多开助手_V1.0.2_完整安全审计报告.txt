微信 · 企业微信多开助手 V1.0.2 完整安全审计报告
====================================================

文档编号：WD-SA-2026-09-13-V102
报告版本：1.0
审计日期：2026-09-13（Asia/Tokyo）
审计对象：PascalePaF/wechat-wecom-duokai，V1.0.2 分支及候选发布文件


一、先说结论
------------

截至本报告完成时，没有发现 V1.0.2 存在后台上传隐私数据、读取聊天记录或账号凭据、
远程控制、静默下载、广告 SDK、挖矿、开机自启、DLL 注入、Hook、修改微信/企业微信
客户端二进制文件等恶意链条。

这个结论不是只看“杀毒软件有没有报毒”，而是由以下相互独立的证据共同支持：

1. 对本仓库 C#、XAML、项目文件、配置、资源和构建脚本执行全量静态检查；
2. 核对所有联网、进程、句柄、注册表、文件删除和持久化相关 API；
3. 核对解决方案的直接及传递依赖，四个项目均没有 NuGet 包引用；
4. 将 UI 与系统级逻辑拆开，复核独立 WechatDuokai.Core 的完整代码边界；
5. 执行自动验证和隔离安装，确认安装完成后应用仍未启动；
6. 使用本机 Kaspersky 的完整病毒库、关闭 iChecker/iSwift、扫描全部对象并只报告；
7. 核对发布文件的 Authenticode 状态，并明确记录当前仍未进行商业代码签名。

风险结论不是“绝对安全”。当前最主要的剩余风险是：为了在已有微信窗口存活时只补开缺少的
窗口，程序需要枚举并关闭精确匹配的单实例锁句柄。该行为没有读取聊天数据，但属于跨进程
句柄操作，可能被启发式/云信誉模型当作高风险特征。第二个风险是文件尚未签名，新的哈希没有
成熟发布者信誉。因此，看到任何新的高危告警时仍应先停止运行并核对哈希、版本和扫描日志，
不应直接点击“忽略”，更不应关闭卡巴斯基或添加整个目录为永久白名单。


二、V1.0.1 那次“高危、启发式/云监测”到底表示什么
------------------------------------------------------

历史中间构建曾被 Kaspersky 实时防护识别为：

    VHO:Trojan.Win32.Convagent.gen
    级别：高
    方法：启发式分析
    来源：云保护

“高危”是安全产品对命中规则的处置等级，不等于实验室已经确认源码中存在某一种木马。
“启发式”表示引擎根据指令组合、行为或结构与恶意程序的相似度判断，而不是精确匹配一条
已知病毒签名。“云监测”表示云端信誉、样本流行度和持续更新的规则参与了判断。未签名、
新生成、自解压、复制自身为卸载器、跨进程句柄操作及延迟自删除等特征叠加时，误报概率会提高。

后续检查没有发现与该通用命名相匹配的恶意闭环：没有网络上传端点、没有命令控制、没有凭据
读取、没有注入、没有隐藏下载、没有未知资源载荷。V1.0.2 又进一步收窄了进程权限并拆分核心。
所以目前最准确的判断仍是：那次告警缺少第二项证据支持，误报可能性较高；但只有 Kaspersky
病毒实验室能对某个具体隔离样本作最终误报裁定。本报告不会把“可能误报”改写成“可以忽略”。


三、V1.0.2 做了哪些安全相关变化
----------------------------------

1. 界面从 WinForms/GDI+ 自绘迁移到 WPF，删除旧的 PremiumControls 大型手绘控件代码。
2. 新建 WechatDuokai.Core 类库；主界面不再直接编译底层句柄实现。
3. 打开目标进程时只请求 PROCESS_DUP_HANDLE（0x0040），不请求 PROCESS_ALL_ACCESS。
4. 不启用 SeDebugPrivilege，不结束微信或企业微信进程。
5. 只处理当前 Windows 会话内、可执行路径与已检测客户端路径一致的目标 PID。
6. 只关闭允许对象类型、白名单锁名称，或精确匹配微信 4.x lock.ini 路径的句柄。
7. 路径无法确认时失败关闭，不凭进程名称猜测后继续操作。
8. 安装器嵌入的有效载荷固定为本版本主程序、配置、Core DLL 和许可证。
9. 安装完成后进入独立完成态，主程序仍未启动；只有“确认并启动”按钮可以启动应用。
10. 绿色版明确要求 Core DLL 与主程序放在同一目录，避免用户误用来源不明的同名 DLL。


四、隐私与联网代码检查
----------------------

在程序源码和构建配置中没有发现以下能力：

- HttpClient、WebClient、WebRequest、TCP/UDP Socket、WebSocket、FTP；
- 上传文件、上传字符串、远程日志、遥测、崩溃上报或在线配置；
- 下载可执行文件、下载补丁、在线更新器或远程脚本；
- 读取微信聊天数据库、消息、联系人、Cookie、Token、密码或登录凭据；
- CreateRemoteThread、WriteProcessMemory、VirtualAllocEx、SetWindowsHookEx；
- 修改、替换或补丁微信/企业微信 EXE、DLL；
- PowerShell、cmd.exe、wscript、cscript 或隐藏命令执行链；
- 计划任务、服务、浏览器扩展或开机启动项。

源码中出现的 Base64 只用于把完整卸载计划里的本地 Windows 路径安全地逐行编码，随后由同一
清理器还原；它不是代码载荷，也不会联网。程序的 GitHub 链接仅在用户点击“开源项目”时交给
系统浏览器打开，不会在后台请求网络。


五、预期存在的敏感系统行为
--------------------------

下列行为属于功能实现，不应被隐藏，也可能提高启发式敏感度：

1. NtQuerySystemInformation / NtQueryObject
   用途：枚举当前系统句柄并读取对象类型、名称，以识别单实例锁。

2. OpenProcess(PROCESS_DUP_HANDLE) / DuplicateHandle
   用途：只复制或关闭白名单内的目标锁句柄，使已经关闭的单个窗口能够重新启动。

3. HKCU\SOFTWARE\Tencent\WXWork\multi_instances
   用途：按当前目标数量写入企业微信当前用户多开提示；不写系统级 HKLM。

4. 当前用户卸载注册表、桌面和开始菜单快捷方式
   用途：安装版正常注册和卸载；绿色版不写入安装注册信息。

5. MoveFileEx(..., MOVEFILE_DELAY_UNTIL_REBOOT)
   用途：完全卸载器无法立刻删除自己的时候，安排清理器及临时工作目录在重启后清除。

这些 API 本身既可用于正常软件也可被恶意软件滥用。判断时要看完整调用链：本版本没有把它们
与联网、注入、凭据读取或未知载荷连接起来，并在 PID、会话、路径、对象类型和锁名称上设有限制。


六、依赖与供应链检查
--------------------

解决方案包含四个项目：

- duokai：WPF 主程序，.NET Framework 4.8 x64；
- WechatDuokai.Core：定位、计数、缓存和锁处理类库；
- installer：WPF 安装器/完整卸载器，.NET Framework 4.8 x64；
- WechatDuokai.Tests：本地自动验证程序。

“dotnet list duokai.sln package --include-transitive”的结果是四个项目均没有包引用。
运行时依赖来自 Windows/.NET Framework 自带程序集，没有 React、WebView、Tauri、Electron、
Python 运行时、广告 SDK 或远程包下载。构建过程没有预构建/后构建下载步骤。


七、安装、启动与删除边界
------------------------

隔离安装测试使用默认目录 %LOCALAPPDATA%\Programs\WechatDuokai：

- 安装前后正在运行的 wechat_duokai 进程数保持不变；
- 安装目录内主程序、配置和 WechatDuokai.Core.dll 均成功落盘；
- 安装完成页明确显示“应用尚未启动”；
- 只有第二次点击“确认并启动”才允许调用 Process.Start；
- 隔离测试目录随后通过安全清理移除；
- 用户原有的 D:\中文安装地址\wechat_duokai 及其中运行中的旧版本没有被覆盖或结束。

完全卸载仍分两档。删除源码的档位必须同时满足专用标记、项目结构、规范化路径、不是磁盘根目录、
不是关键系统目录、不是目录联接/符号链接，并经过复选框和最后对话框确认。即便如此，“删除源码”
仍不可恢复；未推送的本地改动不能靠 GitHub 找回。

九、签名与文件信誉
------------------

V1.0.2 主程序、Core DLL 和安装器当前 Authenticode 状态均为 NotSigned。未签名不等于有病毒，
但会让 Windows SmartScreen 和杀毒云端缺少“谁发布了它、该发布者长期是否可信”的信号。

用户应：

1. 只从 https://github.com/PascalePaF/wechat-wecom-duokai/releases 下载；
2. 确认版本为 v1.0.2；
3. 使用同一 Release 的 SHA256SUMS.txt 核对文件；
4. 保持卡巴斯基开启并更新病毒库；
5. 如果仍报高危，先隔离并保存告警名称、时间、文件路径和 SHA-256，再与 Release 哈希比对；
6. 不要因为本报告就点击“忽略”、恢复隔离对象或设置永久白名单。

下一版最值得优先投入的是可信代码签名和可复现发布流水线。代码签名不能代替源码审计，但能
显著改善发布者身份、下载完整性和云信誉链条。

十一、整体风险评级
------------------

已确认恶意代码：未发现
后台隐私上传：低（代码中无网络实现；没有数据采集链）
聊天数据访问：低（无数据库、消息或凭据读取代码）
底层兼容性：中（依赖 Windows 内部句柄信息和腾讯客户端锁名称）
安全软件误报：中（跨进程句柄、自解压/自清理、未签名新哈希）
供应链：低至中（零第三方包，但仍依赖本机编译环境且当前未签名）
卸载误删：低（多重边界和确认；无法抵御已控制同一用户账户的攻击者）
当前审计置信度：中高（静态、依赖、测试、隔离安装和当天完整病毒库扫描一致）


十二、最终建议
--------------

V1.0.2 可以作为公开测试版发布，但不应该把“公开源码 + 本机零检出”宣传成绝对安全。
目前没有证据支持“原项目在后台上传隐私数据”这一猜测；真正造成告警敏感度的可解释因素是
句柄操作、安装器内嵌载荷、清理器自删除、未签名和新哈希信誉不足。

对用户：不要盲目忽略高危告警；核对来源、版本、SHA-256 和最新扫描日志，无法一致时停止运行。
对项目：V1.0.3 优先做签名、客户端版本兼容矩阵、本地脱敏诊断和更多 DPI/UI 自动回归；继续保持
零联网、零注入、零补丁、最小权限和不读取聊天数据的边界。
