# V1.0.5 设置、实时状态与注册表冲突保护验证报告

文档编号：`WD-VAL-2026-09-16-V105`

验证对象：`PascalePaF/wechat-wecom-duokai` V1.0.5

验证日期：2026-09-16（Asia/Tokyo）

## 1. 结论

V1.0.5 在不改变 V1.0.4 多开边界的前提下，完成了四项可验证改进：

1. 主窗口左下角以两行、左对齐方式实时显示微信与企业微信的根窗口数量；刷新周期为 2 秒，启动或补开
   结束后还会立即刷新一次。
2. 页脚最右侧增加“设置”入口。设置页在同一个窗口的主内容区切换，不创建难以管理的第二窗口，也不
   引入滚动条；可以选择跟随 Windows、固定日间、固定夜间，以及启用或关闭启动时版本检查。
3. 企业微信 `multi_instances` 恢复逻辑加入外部冲突保护。助手只会在当前注册表状态仍等于自己设置的
   临时状态时恢复旧值；若第三方程序在启动期间写入新值，助手保留新值并放弃覆盖。
4. 新增 GitHub Actions 干净 Windows 构建门禁：在全新 GitHub 托管 Windows Server 2022 虚拟机中
   重新编译、执行测试、生成安装版和绿色版、复核 SHA-256，并使用 Microsoft SBOM Tool 生成及验证
   SPDX 2.2 软件物料清单。

## 2. 实时窗口计数

### 2.1 计数口径

页脚显示：

```text
当前微信窗口 x 个
当前企业微信窗口 x 个
```

这里的 `x` 不是简单的同名进程总数。微信 4.x 的一个窗口可能包含多个同名父子进程；核心层先按当前
Windows 用户会话和经过验证的客户端完整路径过滤，再根据父子关系计算根实例。因此页脚、应用卡片和
“补到目标数量”的判断使用相同口径。

### 2.2 刷新行为

- 窗口载入时立即刷新；
- 后台每 2 秒刷新；
- 启动/补开流程结束后立即刷新；
- 即使一次启动流程正在进行，页脚计数仍会更新；
- 未找到有效客户端或枚举瞬间失败时显示 0，不把异常传播到界面线程。

自动测试使用两个互相独立的假客户端路径和可重复的进程快照，验证微信为 2、企业微信为 3 时，页脚
分别准确显示对应文本，且两个文本块保持左对齐。

## 3. 设置页与更新边界

### 3.1 主题

设置页提供三个互斥选项：

- 跟随 Windows 系统；
- 日间主题；
- 夜间主题。

旧版本保存的 `Light`/`Dark` 偏好继续兼容。选择“跟随 Windows”时，窗口重新获得焦点会复核系统应用
主题；若系统主题已改变，界面资源和原生标题栏会同步刷新。页眉原有的日/夜快捷按钮仍保留，点击后会
切换为明确的日间或夜间偏好。

### 3.2 版本检查

“自动更新”在本版被实现为“启动时自动检查新版本”，而不是静默更新器：

- 只向 GitHub 官方 API 读取本项目最新 Release 的 `tag_name`；
- 不在应用内下载附件；
- 不静默安装、覆盖或执行网络文件；
- 不上传诊断报告、客户端路径或账号数据；
- 用户可关闭启动检查，也可随时点击“立即检查”；
- 真正下载只能由用户点击入口后在系统浏览器的 GitHub Releases 页面完成。

这个实现同时满足“设置里可控制自动更新”和项目此前“不在客户端内自动更新”的安全约束。

## 4. 企业微信注册表外部冲突保护

### 4.1 原问题

V1.0.4 会在启动会话开始前保存 `HKCU\SOFTWARE\Tencent\WXWork\multi_instances` 的存在状态、值和
注册表类型，结束时恢复快照。该方式能处理助手自身的正常退出路径，但若其他管理工具在助手启动企业
微信期间主动写入一个新值，旧逻辑可能用更早的快照覆盖第三方的新设置。

### 4.2 V1.0.5 算法

V1.0.5 保存两份状态：

1. `originalState`：进入会话前的原始状态；
2. `temporaryState`：本助手成功写入的临时状态。

结束会话时按以下顺序处理：

```text
读取当前状态
    │
    ├─ 当前状态 == temporaryState ──> 恢复 originalState
    │
    └─ 当前状态 != temporaryState ──> 判定有外部变更，跳过恢复
```

比较范围包括：值是否存在、`RegistryValueKind`、标量内容、二进制数组内容和多字符串数组内容。双开临时
状态是 `DWORD 2`；三开及以上临时状态是“值不存在”。

### 4.3 自动验证

测试在随机的 `HKCU\SOFTWARE\WechatDuokai\Tests\...` 隔离路径运行，不修改真实企业微信设置，并覆盖：

- 原值为字符串时，三开临时删除后可原样恢复值和类型；
- 原本不存在时，双开临时写入后不残留；
- 双开期间第三方将临时 `DWORD 2` 改成 `DWORD 7`，会话结束后仍为 7；
- 三开期间第三方在临时缺失状态下写入 `external-owner`，会话结束后该值仍被保留；
- 企业微信 1→3 的增量启动编排、100ms 交接等待和 800ms 稳定等待仍通过。

### 4.4 边界

Windows 注册表没有为普通值提供跨进程原子 compare-and-swap；因此“读取后、恢复前”仍存在极短的理论
竞态窗口。项目使用命名信号量协调本助手自己的多个进程，并通过恢复前比较保护第三方写入，但不能把它
描述成数据库级事务。后续可研究注册表通知与崩溃恢复日志，进一步缩小窗口。

## 5. GitHub Actions 供应链门禁

工作流文件：`.github/workflows/windows-release-validation.yml`

触发条件：主分支、版本分支、版本标签、Pull Request 和手动运行。

门禁步骤：

1. GitHub 为任务分配一台新的 `windows-2022` 托管虚拟机；
2. 使用固定提交哈希引用 checkout、setup-dotnet、setup-msbuild 和 upload-artifact，降低浮动标签风险；
3. 用 MSBuild Release 配置从源码重建全部程序集；
4. 运行仓库的完整自动测试；
5. 生成安装器、独立清理器、绿色 ZIP、发布清单和 `SHA256SUMS.txt`；
6. 逐项重新计算并核对 `SHA256SUMS.txt`；
7. 安装固定版本 `Microsoft.Sbom.DotNetTool 4.1.2`，生成 SPDX 2.2 SBOM 并执行验证；
8. 把经过测试的包、哈希、SBOM 和验证结果作为 Actions 工件上传。

GitHub 官方文档说明，标准托管 Windows runner 的每个任务使用新的虚拟机：
<https://docs.github.com/en/actions/reference/runners/github-hosted-runners>。Microsoft SBOM Tool 的生成和
验证参数来源：<https://github.com/microsoft/sbom-tool>。

本地 Kaspersky 扫描仍是正式 GitHub Release 的额外发布门禁；云端工作流不会伪装成卡巴斯基扫描。

## 7. 安全结论

本版没有加入客户端注入、内存写入、远程线程、客户端文件修改、静默下载、静默执行、账号数据访问或
诊断上传。新增网络行为仍只有用户允许的 GitHub 版本元数据读取。新增注册表保护减少了覆盖第三方设置
的风险，但并不把企业微信扩展模式包装为腾讯官方承诺的兼容能力。
