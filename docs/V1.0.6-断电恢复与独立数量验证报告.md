# V1.0.6 断电恢复、独立目标数量与程序目录存储验证报告

文档编号：`WD-V106-RECOVERY-STORAGE-20260916`

验证对象：`PascalePaF/wechat-wecom-duokai` V1.0.6

验证日期：2026-09-16（Asia/Tokyo）

## 1. 结论

V1.0.6 完成三项要求：

1. 企业微信临时注册表操作在修改前建立强制落盘的恢复事务；正常退出、程序崩溃、被强制结束或突然
   断电后，都有明确的后续恢复路径。
2. 微信和企业微信拥有彼此独立的目标窗口数量，分别缓存，分别用于对应客户端的补开计算。
3. 设置、主题、诊断、恢复事务和恢复审计等持久运行文件全部位于主程序所在目录的 `data` 子目录。

断电恢复不会削弱 V1.0.5 的外部冲突保护。恢复前仍会比较“存在性、注册表类型、实际值”；任何一项
不再等于助手的临时状态，就视为第三方已接管，不写入旧快照。

## 2. 程序目录内的数据布局

```text
<程序目录>
├─ wechat_duokai.exe
├─ WechatDuokai.Core.dll
├─ wechat_duokai-uninstall.exe          安装版
└─ data
   ├─ .wechat-duokai-user-data          目录身份标记
   ├─ settings.ini                      两项目标、更新偏好、自选客户端路径
   ├─ theme.ini                         跟随系统/日间/夜间偏好
   ├─ diagnostics
   │  └─ diagnostic-*.txt               用户主动生成的本地诊断
   ├─ recovery
   │  └─ wecom-registry-transaction.ini 仅在未完成注册表事务期间存在
   └─ logs
      ├─ registry-recovery.log          当前恢复审计
      └─ registry-recovery.log.1        最多一份轮换日志
```

以下项目不是运行数据文件，而是 Windows 安装集成项：开始菜单快捷方式、可选桌面快捷方式、当前用户的
“已安装的应用”卸载登记。完整卸载会移除这些项目。清理器为删除正在使用的安装目录，会把自身短暂复制
到系统临时目录；该副本执行完后使用 Windows 延迟删除机制安排自删除，不是持久配置位置。

### 2.1 链接与权限保护

- `data` 必须是程序目录的真实子目录；程序拒绝把它作为目录联接或符号链接使用。
- 程序启动时先确认 `data` 可创建、可写；失败时明确提示目录权限并停止，不回退到 AppData 或其他隐藏位置。
- 安装器默认使用当前用户可写的 `%LOCALAPPDATA%\Programs\WechatDuokai`，也允许用户选择其他专用目录。
- V1.0.5 及更早版本的 `settings.ini`、`theme.ini` 会复制到新目录；复制成功后删除旧文件。锁定的旧文件
  不会强删，后续启动或完整清理仍可处理。

## 3. 两项目标数量

配置键拆分为：

```ini
WeChatTargetInstanceCount=3
WeComTargetInstanceCount=2
```

行为：

- 两者范围均为 1–10；
- 两个输入框、减号和加号彼此独立；
- 点击微信只读取微信目标，点击企业微信只读取企业微信目标；
- 旧配置只有 `TargetInstanceCount` 时，两者都以旧值为初值；第一次保存独立值后转换为新键；
- 实际启动仍使用“对应目标 − 对应当前根实例数”，不会因为另一类客户端的目标而多开。

## 4. 恢复事务的写入顺序

企业微信需要临时处理 `HKCU\SOFTWARE\Tencent\WXWork\multi_instances`。V1.0.6 的顺序为：

```text
取得本助手命名信号量
  ↓
处理可能存在的旧恢复事务
  ↓
读取原始注册表状态（存在性、类型、值）
  ↓
计算本次预期临时状态
  ↓
在 data\recovery 写入同目录临时文件
  ↓
FileOptions.WriteThrough + Flush(true)
  ↓
原子改名为正式事务文件
  ↓
修改并 Flush 注册表
  ↓
启动/补开企业微信
  ↓
条件恢复并删除事务文件
```

只有事务文件已经完成落盘，注册表才会被修改。事务记录：格式版本、随机事务号、创建时间、所有者 PID、
所有者进程启动时间、固定注册表路径和值名、原始状态、预期临时状态。注册表字符串或数组使用 Base64
只是为了可靠序列化特殊字符，不是加密。

## 5. 崩溃和断电后的恢复决策

下次启动时先取得同一命名信号量，再读取事务：

| 条件 | 行为 |
| --- | --- |
| 没有事务文件 | 不操作注册表 |
| 原所有者 PID 与启动时间仍匹配活进程 | 暂缓恢复，保留事务 |
| 当前状态完全等于事务中的临时状态 | 恢复原始状态并删除事务 |
| 当前状态不等于临时状态 | 认定外部程序已修改；保留外部状态并删除旧事务 |
| 日志损坏、目标路径不匹配 | 隔离无效日志，不修改注册表；隔离文件存在期间不开始新的临时会话 |
| 注册表暂时不可访问 | 保留事务，下次启动重试 |

恢复支持 `REG_DWORD`、`REG_QWORD`、`REG_SZ`、`REG_EXPAND_SZ`、`REG_MULTI_SZ`、`REG_BINARY` 和缺失值，
同时恢复原始 `RegistryValueKind`，不是把所有值强制转成数字或字符串。

## 6. 断电时序分析

| 中断点 | 下次启动结果 |
| --- | --- |
| 事务文件落盘前 | 注册表尚未修改，无需恢复 |
| 事务落盘后、注册表修改前 | 当前状态通常仍是原值；因不等于临时值而保留，不做多余覆盖 |
| 注册表修改后、企业微信启动前 | 当前状态等于临时值，恢复原值 |
| 企业微信启动期间 | 当前状态等于临时值时恢复；外部更改时保留外部值 |
| 原值已恢复、事务文件删除前 | 当前状态不等于临时值，保留当前原值并清理旧事务 |

普通 Windows 注册表值没有跨进程的 compare-and-swap。另一个程序仍可能恰好在“最后一次比较”和
“恢复写入”之间修改同一个值；这是公开的剩余竞态。命名信号量只协调本助手实例，不能强制第三方遵守。

## 7. 恢复审计与隐私

`data\logs\registry-recovery.log` 记录时间、事务号、结果和原因，例如：

```text
JOURNAL_DURABLE transaction=<id> ownerPid=<pid>
SESSION_APPLIED transaction=<id> target=3 ownerPid=<pid>
REGISTRY_RESTORED transaction=<id> reason=startup
EXTERNAL_STATE_PRESERVED transaction=<id> reason=startup
```

它不写入原始注册表内容、客户端账号、聊天内容、用户名、命令行或凭据。日志超过 256 KiB 后只保留一份
`.1` 轮换文件，避免无限增长。

## 8. 自动化验证

V1.0.6 自动化测试覆盖：

1. 微信和企业微信默认均为 2，分别保存 7 与 4 后互不覆盖；
2. 两个 UI 输入框存在、标识正确，最小尺寸和最大化比例布局不裁切；
3. 正常双开临时 DWORD 2，结束后恢复缺失值；
4. 正常扩展模式临时删除值，结束后恢复原字符串及类型；
5. 临时 DWORD 2 被第三方改成 DWORD 7/9 时，结束或重启恢复均保留第三方值；
6. 真实启动子测试进程，建立事务和临时注册表状态后不调用 `Dispose` 直接退出；父进程随后成功恢复；
7. 异常扩展模式恢复 `REG_MULTI_SZ`，内容、顺序和类型完全一致；
8. 正常结束和已处理外部冲突都不留下活动事务文件；
9. 审计日志包含恢复与冲突结果，但不包含原始注册表字符串；
10. 伪造的无效事务被隔离，当前注册表保持不变；
11. 设置、主题、恢复事务、审计和诊断路径均位于程序目录；
12. 安装测试确认安装目录内创建带身份标记的 `data`；
13. 带正确标记的旧设置和主题迁移到新 `data`，旧单一目标同时成为两项目标初值，空旧目录被移除；
14. 原有进程统计、补开、客户端签名、安装覆盖、删除边界、UI 和锁处理回归继续通过。

## 9. 结论边界

- “强制落盘”显著缩小了断电丢失恢复信息的窗口，但消费级硬件、磁盘控制器和文件系统故障仍不能提供
  绝对不可丢失保证。
- 同一 Windows 用户本来就能修改该用户的文件和 HKCU 注册表；恢复日志用于故障恢复和误覆盖保护，
  不是抵御已完全控制同一账户的恶意程序的密码学边界。
- 本功能不修改企业微信文件、不注入 DLL、不读取聊天数据，也不把恢复日志上传到网络。
